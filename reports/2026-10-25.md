## Verilator：大 DPI 数组不再展开成海量转换语句

**FPGA / HDL 仿真 · OCT 25 MAIN · 非正式发行**

06:03 合入 e4d92cb：DPI unpacked array 参数转换从逐元素生成语句，改为按数组维度生成循环，避免大数组导致巨大 C++ 函数和慢编译。区别于 23 日的仿真线程同步，这是 SystemVerilog 与 C/C++ 交互处的编译规模问题，适合图像帧缓冲、内存模型及大批数据的验证平台。

Verilator 为 LGPL-3.0 / Artistic-2.0 双许可；CPU 编译即可，Linux/WSL 是方便的复现环境，无 GPU 或上板要求。固定该提交及相同 C++ 编译器，用现有 DPI 测试比较生成文件大小、编译时间、峰值 RAM，并检查输入/输出/inout、多维数组的结果。提交给出机制修复，没有公布统一提速倍数；转换仍要遍历数据，不等于零拷贝，也不承诺仿真运行更快。没有新增 FPGA 器件、综合时序或资源数据。

SystemVerilog DPI · 按维生成循环 · CPU / Linux 或 WSL · 无新器件 · 编译规模优化 ≠ 零拷贝或实测倍数

## 今日深挖：Verilator DPI：优化生成程序的规模，也是一种性能工程

这次值得精读的是生成器，而不是某条更快的算术指令。旧实现按数组元素生成转换语句，数组越大，交给 C++ 编译器的函数越庞大；新实现为每一维生成循环，用索引对应内部多维布局和 DPI 的线性表示，保留元素转换，却不再让顶层代码随元素数展开。收益首先指向生成代码规模和编译资源，运行时仍有数据遍历，不能推导出零拷贝或更低仿真延迟。建议做一个可控的多维 DPI 数组示例，逐步增大尺寸，分别记录生成 C++ 大小、生成/编译耗时、峰值内存及仿真输出；再覆盖 input/output/inout、位向量和结构体。固定父提交与新提交、相同编译器/选项，才知道问题是否真正缓解。本次仅审阅提交，没有编译测试、跑仿真或上板。

## 信号与噪音

判断而非事实：‘结构化输出’容易被当作 Agent 可靠性的保证。vLLM 的迁移提示恰好说明，后端一换，正则语义、允许的 token 和格式都可能变化；JSON 能解析仍不能保证内容正确、调用适当或权限成立。更值得保留的是固定版本、真实边界输入的回归集、失败记录与回滚路径。类似地，端侧多核优化要看设备实测，机器人登榜要看新增代码、权重和实机证据，不能用热度填补缺失的验证。
